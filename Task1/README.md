# Задание 1. Анализ безопасности системы

# Аудит безопасности данных и план улучшений

## 1. Выявленные проблемные зоны

В результате анализа архитектуры As-Is и бизнес-процессов компании "Медикаменте" выявлены следующие критические несоответствия требованиям безопасности и лучшим практикам:

### 1.1 Отсутствие инвентаризации и классификации данных
*   **Проблема:** Нет четкого реестра конфиденциальных данных (PII, медицинские, платежные). Данные хранятся бессистемно в Excel и файловых папках, названных по ФИО пациентов, что само по себе является утечкой.
*   **Риски:** Невозможно гарантировать защиту того, что не учтено. Нарушение ФЗ-152 "О персональных данных" (ст. 18.1, обязанность оператора принимать меры, необходимые и достаточные для обеспечения выполнения обязанностей).

### 1.2 Хранение данных в открытом виде
*   **Проблема:** Все данные (Excel, PDF, JPG) хранятся на файловом сервере без какого-либо шифрования. Доступ к папкам, названным по ФИО, фактически раскрывает связи между данными.
*   **Риски:** При компрометации файлового сервера или рабочей станции сотрудника злоумышленник получает полный доступ ко всем данным компании. Нарушение ст. 19 ФЗ-152 (обязанность оператора обеспечивать конфиденциальность ПДн).

### 1.3 Отсутствие контроля доступа (RBAC/ABAC)
*   **Проблема:** Доступ к данным ограничен только доменной аутентификацией. Любой сотрудник, имеющий доступ к файловому серверу или общим папкам, может теоретически просматривать данные любых пациентов. Врачи имеют доступ к журналам друг друга.
*   **Риски:** Высокий риск инсайдерских утечек и непреднамеренного разглашения данных. Нарушение принципов минимизации данных (Data Minimization) и Privacy by Design.

### 1.4 Отсутствие аудита действий
*   **Проблема:** Системы не логируют, кто, когда и к каким данным обращался, а также какие изменения вносил. Невозможно отследить цепочку действий с данными (Data Lineage).
*   **Риски:** Невозможно расследовать инциденты утечек, подтвердить compliance, обеспечить неотказуемость (non-repudiation). Нарушение требований к защите от несанкционированного доступа (НСД).

### 1.5 Небезопасная передача данных
*   **Проблема:** Данные передаются между системами и людьми по незащищенным каналам:
    *   Устно/бумажно (пациент -> ресепшен).
    *   По электронной почте без шифрования (лаборатория -> компания).
    *   По внутренней сети без шифрования (все взаимодействия с файловым сервером).
*   **Риски:** Перехват данных, а также нарушение врачебной тайны уже на этапе коммуникации с пациентом в холле клиники.

### 1.6 Избыточное дублирование данных
*   **Проблема:** Данные многократно дублируются вручную (кассир дублирует платежи из Excel в 1С), что увеличивает поверхность атаки и риск ошибок/утечек. Нет единого источника правды (Single Source of Truth).
*   **Риски:** Несогласованность данных, сложность обеспечения их целостности и контроля доступа.

### 1.7 Использование устаревших и небезопасных протоколов
*   **Проблема:** Взаимодействие между ККМ и 1С через OLE и TCP/IP, а также интеграция между базами 1С через OLE, не предусматривает современных механизмов шифрования и аутентификации.

## 2. Предлагаемые улучшения и механизмы защиты

Для устранения выявленных проблем предлагается внедрить следующие меры, основанные на принципах Privacy by Design и Data Minimization.

### 2.1 Классификация данных и механизмы защиты

| Категория данных | Примеры | Уровень критичности | Способ защиты при хранении | Способ защиты при передаче |
| :--- | :--- | :--- | :--- | :--- |
| **Прямые идентификаторы** | ФИО, Паспортные данные, Телефон, Email, Адрес | Критичный | Шифрование (AES-256) | TLS 1.3, маскирование в логах |
| **Медицинские данные (врачебная тайна)** | Диагнозы, Результаты анализов, Жалобы | Критичный | Шифрование (AES-256) | TLS 1.3, обезличивание для аналитики |
| **Платежные данные** | Суммы, даты оплат, идентификаторы транзакций | Высокий | Шифрование (AES-256) | TLS 1.3 |
| **Квази-идентификаторы** | Дата рождения, Пол | Средний | Псевдонимизация (замена на токен или хеш с солью) | TLS 1.3 |
| **Данные о действиях (логи)** | История обращений к данным, действия в системе | Средний | Целостность (цифровая подпись), шифрование | TLS 1.3 |

### 2.2 Механизм тегирования данных (Data Tagging)

Необходимо внедрить систему, где каждый объект данных (файл, запись в БД) будет иметь метки (теги), определяющие правила работы с ним.
*   **Типы тегов:**
    *   `PII`: Содержит персональные данные.
    *   `MEDICAL`: Медицинская тайна.
    *   `RESTRICTED`: Ограниченный доступ (например, для определенных ролей).
    *   `RETENTION_POLICY`: Срок хранения (например, 1 год, 5 лет, бессрочно).
    *   `MASKED`: Данные, которые должны отображаться в маскированном виде для некритичных ролей (например, администратор видит только последние 4 цифры паспорта).
*   **Применение:** Теги должны присваиваться автоматически при поступлении данных в систему на основе контента или вручную администратором безопасности.

### 2.3 Инструменты, способы и меры для обеспечения конфиденциальности

1.  **Внедрение системы управления доступом (IAM):**
    *   Инструменты: Keycloak, Okta, или встроенные механизмы будущей CRM.
    *   Меры: Внедрение ролевой модели (RBAC) и, в перспективе, атрибутной (ABAC) на основе тегов данных. Например: доступ к данным с тегом `MEDICAL` есть только у роли `Врач` и `Пациент` (к своим данным).

2.  **Шифрование данных:**
    *   **Хранение:** Использование прозрачного шифрования данных (TDE) на уровне баз данных и шифрование файлов в объектном хранилище (например, с использованием AWS KMS или HashiCorp Vault).
    *   **Передача:** Использование TLS 1.3 для всех внешних и внутренних коммуникаций (между микросервисами, между сервисами и базами данных).

3.  **Маскирование и обезличивание данных (Data Masking):**
    *   Динамическое маскирование (Dynamic Data Masking): Сотрудник ресепшена видит только `+7 (***) ***-**-56` при работе с порталом.
    *   Обезличивание (Anonymization): Для аналитических задач (BI, ML) данные проходят через ETL-процесс, который удаляет или заменяет все идентификаторы на необратимые значения.

4.  **Аудит и мониторинг (Audit & Monitoring):**
    *   Инструменты: SIEM-система (например, Wazuh), сбор логов из всех компонентов (БД, API-шлюзов, приложений).
    *   Меры: Логирование всех операций доступа к данным с тегами `PII` и `MEDICAL`. Настройка алертов на нестандартные действия (например, врач скачивает папки 50 разных пациентов за минуту).

5.  **Управление ключами (KMS):**
    *   Инструменты: HashiCorp Vault.
    *   Меры: Централизованное хранение и ротация ключей шифрования, строгий контроль доступа к ним.

6.  **API-шлюз (API Gateway):**
    *   Инструменты: KrakenD, Kong, Spring Cloud Gateway.
    *   Меры: Централизованная проверка прав доступа на основе токенов (JWT), rate limiting, маскирование чувствительных полей в ответах API в соответствии с политиками.

## 3. Доработанные диаграммы потоков данных (To-Be)

На обновленных диаграммах ниже показано, как предлагаемые механизмы встраиваются в потоки данных. Ключевые изменения:

*   Разделение хранилищ на "сырые" данные (озеро данных) и подготовленные, обезличенные данные для аналитики.
